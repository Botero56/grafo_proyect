## 1. Arquitectura general (para ubicarse)

```
WhatsApp Cloud API (Meta)
        │  POST /api/v1/webhook  (un solo endpoint para TODO)
        ▼
app/api/v1/webhook/router.py
        │  1. valida X-Hub-Signature-256 (signature.py)
        │  2. WhatsAppWebhookEventRouter.route(payload) clasifica el evento
        ▼
┌───────────────────────────────────────────────────────────┐
│ WhatsAppWebhookEventRouter (webhook_event_router.py)       │
│  field="messages"        → WhatsAppWebhookService           │
│  field="smb_message_echoes" → _process_echo (pausa el bot)  │
│  field="history"/"smb_app_state_sync" → solo se auditan     │
└───────────────────────────────────────────────────────────┘
        │  (mensaje de cliente/admin)
        ▼
_process_customer_message (router.py)
        │  1. ¿bot_activo? si no, ¿toca auto-reactivar?
        │  2. resolve_role (admin/cliente) — SIEMPRE en el backend, nunca la IA
        │  3. si admin + imagen/botón: MenuIngestionOrchestrator intercepta
        │  4. MessageDebouncer.debounce(...) agrupa mensajes seguidos
        ▼
AgentRunnerService.get_reply (ADK Runner + FirestoreSessionService)
        │  ejecuta el Agent (admin_agent o user_agent) con sus tools
        ▼
OutboundMessageService.send_and_persist → WhatsAppClient → Graph API de Meta
```

Multi-tenant: cada `Business` tiene su propio número de WhatsApp
(`whatsapp_phone_number_id`), su propia `Configurations` (admins, mensaje de
traspaso, etc.), y todas las colecciones relevantes están scoped por
`business_id` vía `TenantScopedQuery` (nadie cruza datos entre negocios).

Colecciones Firestore relevantes: `businesses`, `customers` (subcolección
de business), `conversations` (subcolección de business), `messages`
(subcolección de conversation), `menu_items` (modelo `DailyMenus`, el menú
del día real — ver sección 4), `fixed_menu_items`, `orders`, `webhook_events`
(idempotencia), `configurations`.

## 2. Handoff bot ↔ humano (Coexistencia WhatsApp)

**Problema que resuelve:** el negocio usa la app móvil de WhatsApp Business
*a la vez* que este backend (modo Coexistencia de Meta). Cuando la
encargada le responde a un cliente desde su celular, el bot no debe
seguir contestando por encima de ella.

**Conexión clave — un solo webhook, cuatro tipos de evento:**
`WhatsAppWebhookEventRouter` lee `entry[0].changes[0].field`:

| `field` | Qué es | ¿Pasa por la IA? |
|---|---|---|
| `messages` + `value.messages` | Mensaje del cliente/admin | Sí (si `bot_activo`) |
| `messages` + `value.statuses` | sent/delivered/read/failed | No — solo actualiza `Messages.status` |
| `smb_message_echoes` | Un humano escribió desde el celular | **Nunca** — pausa el bot |
| `history` / `smb_app_state_sync` | Sincronización de Meta | No — solo se guarda para auditoría |

**Estado en `Conversations`:** `bot_activo` (bool), `motivo_handoff`,
`pausado_desde`, `ultimo_mensaje_humano_at`. `HandoffService`
(`app/services/conversation/handoff_service.py`) es el **único** que los
muta:
- `pause_bot(conversation, motivo)` — llamado desde `_process_echo` cuando
  llega un echo real de la encargada.
- `reactivate_bot(conversation)` — manual (tool `reactivate_customer_chat`
  del admin_agent) o automática.
- `should_auto_reactivate(conversation, now)` — true si ya pasaron
  `HANDOFF_QUICK_REACTIVATION_SECONDS` (30s, `app/config.py`) desde
  `ultimo_mensaje_humano_at`/`pausado_desde`.
- `get_transfer_message(business_id)` — lee
  `Configurations.handoff_transfer_message` o usa el default.
- `notify_human(business, customer, motivo)` — avisa a la encargada que el
  bot necesita ayuda (best-effort, nunca rompe el flujo si falla).

**Decisión importante (corregida en vivo, ver §6):** la IA puede pedir
handoff (`request_human_handoff` en `customer_tools.py`, cuando detecta baja
confianza o el cliente pide un humano explícitamente) pero **eso ya NO
pausa el bot** — solo manda el mensaje de traspaso configurado y notifica a
la encargada. El bot sigue atendiendo con normalidad. Lo único que
realmente pausa la conversación es un **echo real** (la encargada
respondiendo desde su celular).

**Reactivación:** ya no requiere autorización manual desde el chat admin.
Es *event-driven*: cuando llega el siguiente mensaje del cliente y ya
pasaron 30s de silencio de la encargada, ese mismo mensaje reactiva el bot
y sigue el flujo normal (se chequea en `_process_customer_message`, no por
un job programado — 30s es demasiado seguido para Cloud Scheduler). Existe
además `HandoffSettings.HANDOFF_INACTIVITY_MINUTES` (240min) como respaldo
de horizonte largo vía `app/services/conversation/reactivation_job.py`
(pensado para correr como Cloud Scheduler).

## 3. Menú del día por imagen (chat admin)

**Flujo:** la encargada manda una foto del menú al chat admin (con o sin
caption indicando la fecha) →
`MenuIngestionOrchestrator` (`app/services/daily_menu/orchestrator.py`)
intercepta el mensaje **antes** de que llegue al `admin_agent` (el rol ya
se resolvió en el backend, ver §1) → descarga+verifica sha256 de la imagen
(`media_downloader.py`) → extrae con Gemini vision un JSON estructurado
(`vision_extractor.py`) con el esquema `plato_del_dia` / `acompanamientos`
/ `otras_opciones` → guarda un borrador (`DailyMenus`, estado
`pendiente_confirmacion`) → manda un mensaje con botones interactivos
(confirmar/corregir/cancelar) por WhatsApp.

- **Confirmar** → el borrador pasa a `activo` para su `fecha_vigencia`
  (resuelta de el caption vía `caption_date_resolver.py`; si pasó la
  medianoche entre subir la foto y confirmarla, se recalcula sola y se
  avisa).
- **Corregir** (texto libre) → `correction_extractor.py` reinterpreta el
  borrador con Gemini y muestra un diff contra el último menú activo
  (`menu_diff.py`) antes de volver a pedir confirmación.
- **Cancelar** → se descarta el borrador.

**Concurrencia:** un lock `asyncio.Lock` por `business_id`
(`_business_locks` en `orchestrator.py`, mismo patrón que
`AgentRunnerService._locks`) evita borradores duplicados si llegan dos
fotos casi simultáneas. Todas las llamadas a Gemini/Firestore están en
`run_in_threadpool` para no bloquear el event loop de FastAPI.

**Conexión con el lado cliente:** `customer_tools.py::get_active_menu` /
`validate_order_items` leen el `DailyMenus` con estado `activo` de **hoy**
— el cliente solo ve el menú confirmado del día, nunca un borrador. Precios
no legibles o datos faltantes en la extracción caen en la lógica de
handoff existente (§2) en vez de que la IA invente datos.

**Recordatorios:** `app/services/daily_menu/reminders.py` — si a las
`DAILY_MENU_REMINDER_HOUR` (9am) no hay menú `activo` para hoy, le
recuerda una vez al admin; si sigue sin confirmar tras
`DAILY_MENU_DISCARD_MINUTES` (90min desde el recordatorio), descarta el
borrador pendiente.

## 4. Unificación de colecciones de menú (`menu_items` ↔ `daily_menus`)

**Problema:** existían dos colecciones Firestore hablando de "menú":
`menu_items` (catálogo plano viejo, con datos de prueba, conectado a varias
partes del código) y `daily_menus` (la real, del flujo de §3). Se
unificaron en **una sola colección física: `menu_items`**, con el modelo
Python `DailyMenus` (`Meta.collection_name = "menu_items"` en
`firebase_schemas.py`). El nombre de la clase Python no cambió — solo la
colección física a la que apunta.

Se migraron los documentos reales de `daily_menus` (incluyendo un menú
`activo` en producción) a `menu_items` con el mismo ID de documento, se
borraron los datos de prueba viejos de `menu_items`, y se confirmó por
consulta directa a Firestore que la colección `daily_menus` ya no existe.
Backups locales (gitignored, fuera de versión) antes de cada borrado.

**Efecto en cascada:** el reporte Excel `"product_catalog"` se eliminó (ya
no hay un catálogo separado que reportar), y todo lo que antes resolvía
nombres de producto vía Firestore (`fetch_menu_items`) ahora usa una lista
estática `PRODUCT_ITEM_LABELS` en
`app/services/excel_report_service/constants.py`:
```python
PRODUCT_ITEM_LABELS = [
    {"item_id": "plato_del_dia", "name": "Menú del día"},  # el nombre debe
    {"item_id": "otras_opciones", "name": "Otras opciones"},  # matchear
]  # LUNCH_STATS_DAILY_MENU_KEYWORD ("menú del día") o rompe la clasificación
```

## 5. Reportes Excel (IA admin) — calidad y contexto

**Antes:** el admin preguntaba "¿cuál es el menú?" y la IA respondía con un
Excel de datos mockeados de versiones anteriores (colisión de nombres con
`product_catalog`, ver §6). Y cualquier reporte con datos vacíos generaba
un Excel confuso.

**Ahora:**
- `admin_tools.py::get_today_menu` — nueva tool dedicada, lee
  `DailyMenuService` directo (el menú real de hoy), sin pasar por Excel.
  El prompt del admin_agent tiene una instrucción explícita de "error que
  ya pasó en producción, no lo repitas" para forzar su uso ante cualquier
  pregunta sobre el menú.
- `generate_excel_report` — antes de generar el archivo, calcula un
  `summary` (`build_report_summary`/`compute_dashboard_summary`/
  `compute_lunch_stats_summary`) y **si no hay datos, no genera el
  archivo** (`status="empty"`, sin Excel confuso). Si hay datos, devuelve
  `{"status": "ok", "file_name", "summary"}` — el `summary` queda en la
  sesión ADK (persistida en Firestore, ver §1) para que el admin pueda
  preguntar cosas puntuales sobre ESE reporte más adelante en la misma
  conversación sin que la IA tenga que volver a llamar a la tool ni abrir
  el archivo.
- `get_customer_chat_reference(phone_number)` — nueva tool: para preguntas
  tipo "¿de qué hablé con Camilo?" la IA **ya no inventa un resumen ni
  genera Excel** — devuelve nombre/teléfono/link de WhatsApp
  (`wa.me/<phone>`) para que el admin abra y lea la conversación él mismo.
- `fetch_conversations` (Excel de conversaciones) ahora cruza con
  `Customers` para mostrar nombre/teléfono legibles en vez de
  `conversation_id`/`customer_id` crudos de Firestore.
- Regla de negocio en el prompt: la IA puede **sugerir** un Excel en texto,
  pero solo lo genera si el admin lo confirma o lo pide explícitamente en
  un mensaje aparte — nunca en la misma respuesta donde lo sugiere.

## 6. Bugs reales corregidos (detectados en producción)

1. **`bot_activo` tratado como pausado sin estarlo.** `fireo` solo aplica
   `BooleanField(default=True)` al serializar una instancia nueva, no al
   leer un campo ausente de Firestore — conversaciones creadas antes de
   que este campo existiera lo tenían `None`. `if not conversation.bot_activo`
   trataba `None` como pausado. Fix: comparar explícito contra
   `is False`. Síntoma reportado: *"escribo desde el chat normal y la ia
   no me responde"*.
2. **`ValueError: max() arg is an empty sequence`** en
   `daily_menu_service.py::get_last_active`. `fireo.fetch()` devuelve un
   `QueryIterator` sin `__bool__`/`__len__`, así que `if not candidates`
   nunca detectaba una lista vacía. Se materializa con `list(...)` en los
   6 sitios donde este patrón se repetía (`reactivation_job.py`,
   `reminders.py` ×2, `tenant_scoped_service.py`, `customer_tools.py`,
   `daily_menu_service.py`).
3. **El bot se quedaba mudo tras un pedido de handoff del cliente.** Se
   pausaba apenas la IA detectaba que el cliente quería un humano, pero
   nada garantizaba que alguien respondiera pronto → cliente sin respuesta
   de nadie. Fix descrito en §2 (solo un echo real pausa).
4. **Admin veía menú mockeado viejo en vez del real.** Colisión de tools:
   "¿cuál es el menú?" caía en `generate_excel_report(report_type=
   "product_catalog")`. Fix: `get_today_menu` dedicada + eliminación del
   reporte `product_catalog` (§4, §5).
5. **Token de WhatsApp expirado no se recargaba.** `main.py` corre
   `uvicorn.run(..., reload=True)` sin `reload_includes` — el autoreload
   de Uvicorn por defecto solo vigila archivos `.py`, **no** `.env**. Al
   refrescar el token en `.env` sin reiniciar el proceso a mano, seguía
   usando el token viejo en memoria. No era un bug de código: se
   diagnosticó consultando `debug_token`/`{phone_number_id}` directo contra
   la Graph API de Meta con `curl` para descartar causas (token inválido,
   caída de Meta — se confirmó que no había incidentes activos).
6. **Respuestas repetidas por mensajes seguidos** — ver §7.

## 7. Agrupar mensajes seguidos antes de responder (último feature)

**Problema:** si el cliente escribía 3 frases en 3 mensajes de WhatsApp
separados (3 webhooks independientes), cada uno se procesaba de inmediato
y la IA respondía 3 veces — respuestas repetidas/redundantes porque cada
una se generaba sin ver los mensajes siguientes.

**Solución — `MessageDebouncer`**
(`app/services/conversation/message_debouncer.py`): agrupa por
`conversation_id`. Cada mensaje nuevo se agrega a un lote y (re)programa un
`asyncio.Task` que espera `_MESSAGE_DEBOUNCE_SECONDS` (6s, constante en
`router.py`) de silencio antes de invocar al agente. Si llega otro mensaje
antes de que se cumpla el plazo, se cancela el envío anterior y se
reprograma — el agente termina viendo **todo el texto acumulado, unido por
saltos de línea, en una sola llamada**. Vive en memoria del proceso, mismo
patrón que `AgentRunnerService._locks`/`HandoffService`.

**Dónde se conecta:** `_process_customer_message` (router.py) se separó en
dos partes:
- Lo que debe seguir siendo **inmediato por mensaje** (sin cambios): guardar
  en Firestore, chequeo de pausa/auto-reactivación, interceptar imágenes de
  menú para el admin (`MenuIngestionOrchestrator`, §3).
- Lo que se **difiere**: generar+mandar la respuesta del agente, ahora en
  `_generate_and_send_reply` (nueva función), invocada por el debouncer
  cuando el remitente lleva 6s en silencio.

Esto es independiente del lock por-conversación que ya tenía
`AgentRunnerService` (§1) — ese lock serializa turnos que sí llegan a
ejecutarse; el debouncer evita que lleguen a ejecutarse por separado en
primer lugar.

Tests nuevos: `tests/test_message_debouncer.py` (mock de `on_flush`,
coalescencia de 3 mensajes en 1, conversaciones independientes no se
mezclan, errores en el flush no rompen el proceso). Tests existentes en
`test_webhook_router_flows.py` actualizados para parchear el delay a 0 y
esperar la tarea en background antes de assertar.

## 8. Marcar el negocio como cerrado un día (`mark_closed_today`)

**Problema que resuelve:** si a la hora del recordatorio
(`DAILY_MENU_REMINDER_HOUR`, ver §3) la encargada responde que ese día
simplemente no abren (vacaciones, remodelación, etc.), antes no había forma
de que un cliente que pregunta por el menú se enterara — la IA de clientes
solo veía `menu_available=False` y lo trataba como "todavía no lo han
subido", ofreciendo esperar o derivando a un humano por falta de datos.

**Conexión — mismo `menu_items`, nuevo estado:**
`DailyMenuStatus.CERRADO` (`app/schemas/enum_schemas.py`) se suma a
`pendiente_confirmacion`/`activo`/`reemplazado`/`descartado`. Un registro
"cerrado" es un documento `DailyMenus` simple (sin `extracted_menu`, solo
`fecha_vigencia`/`status`/`caption` con el motivo) guardado por
`DailyMenuService.mark_closed_today` (`app/services/daily_menu/
daily_menu_service.py`), que:
- descarta cualquier borrador pendiente de esa fecha (mismo criterio que
  `create_draft`),
- reemplaza (`status=reemplazado`) un menú ya confirmado ese día si lo
  había — un día no puede estar cerrado y con menú activo a la vez,
- y si se llama dos veces el mismo día, actualiza el motivo en vez de
  duplicar el registro (idempotente).

**Disparador:** nueva tool `mark_closed_today(motivo)` en el admin_agent
(`app/ai/ai_restaurant/admin/admin_tools.py`, registrada en `admin/
agent.py`). El prompt (`restaurant_admin_agent_prompt.py`) instruye a la
IA a llamarla cuando el admin diga explícitamente que no abren hoy — no
requiere que sea justo en respuesta al recordatorio, funciona en cualquier
momento del día.

**Dónde se lee ese estado:**
- `customer_tools.py::get_active_menu` — antes de mirar si hay menú activo,
  chequea `get_closed_for_date`; si hay registro, devuelve
  `{"menu_available": False, "closed_today": True, "closed_reason": "..."}`
  en vez de la forma genérica de "no disponible todavía". El prompt del
  customer_agent (`restaurant_user_agent_prompt.py`) le avisa al cliente
  que no hay servicio hoy (con el motivo si existe) y explícitamente NO
  ofrece esperar ni dispara `request_human_handoff` para este caso — ya es
  una respuesta completa, no falta ningún dato.
- `admin_tools.py::get_today_menu` — mismo criterio para cuando el propio
  admin pregunta "¿cuál es el menú?": le recuerda que ese día quedó
  marcado como cerrado en vez de decir "no hay menú confirmado".
- `reminders.py::remind_missing_daily_menus` — deja de insistir con "aún no
  tengo el menú de hoy" si el día ya está marcado como cerrado.

Tests nuevos: `test_daily_menu_service.py` (creación, reemplazo de menú
activo, descarte de borrador pendiente, llamada duplicada actualiza el
motivo en vez de duplicar), `test_get_active_menu.py` y
`test_admin_today_menu.py` (forma de respuesta `closed_today`/
`closed_reason`, un cierre en otra fecha no afecta hoy, la tool guarda el
teléfono del admin resolviéndolo desde `tool_context.state["customer_id"]`),
`test_daily_menu_reminders.py` (no se manda el recordatorio si el día ya
quedó cerrado).
